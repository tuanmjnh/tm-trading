# TM Trading — V4.2 service reliability drills

The drill harness (`tools/drills/`) starts the **real supervisor process**, which
forks the **real worker host**, over the **real IPC channel**, against a fixture
registry. The assertions are then made against the same state file the Operations
API and the CLI read.

Nothing is mocked. That is the entire point: a unit test can prove a function
returns the right object, but it cannot prove that a separate OS process spawns,
reports evidence, crashes, backs off, restarts, drains and recovers while another
process watches.

```bash
npm run drills                        # all drills (~30 s on Windows)
node tools/drills/run.mjs --list      # drill names
node tools/drills/run.mjs crash-restart
```

Exit code is non-zero when any drill fails, so CI can gate on it.

---

## 1. What the harness proves — and what it does not

**Proves:**

- the supervisor can spawn a worker, receive its evidence over IPC, and reach
  `READY` only because the evidence justified it;
- a crash is detected, counted, backed off and restarted;
- a graceful supervisor drain is **not** recorded as a crash;
- a supervisor restart restores operator intent (`desired: RUNNING`);
- the command inbox is durable and idempotent: a replayed command produces one
  operation, an expired one is quarantined;
- `reset` clears runtime state without deleting history.

**Does not prove:**

- that a *production* service (news, scanner, funding, liquidation, alerts, …)
  reports its evidence correctly. The fixtures are well-behaved by construction;
- anything about the shared Supabase/Mongo data. The harness sets `MONGODB_URI=''`
  and the fixtures have no database dependency.

Per-service rollout evidence (S3 step 2) therefore still requires an operator run
against the production-like supervisor; see §5.

## 2. Isolation

Every drill gets a throwaway workspace:

```
node_modules/.cache/tm-trading/drills/<drill-name>-<random>/
  supervisor.json     # the state file
  commands/           # the command inbox (+ quarantine/)
  scratch/            # fixture markers (crash.request, crash.done, reset.marker)
```

A drill can never read or consume a real operator's commands: the supervisor
child is started with `TM_SUPERVISOR_STATE` and `TM_SUPERVISOR_COMMANDS` pointed
inside the workspace, and the workspace is deleted when the drill finishes.

Environment handed to the child:

| Variable | Purpose |
| --- | --- |
| `TM_SUPERVISOR_STATE` | state file path (workspace) |
| `TM_SUPERVISOR_COMMANDS` | command inbox path (workspace) |
| `TM_SUPERVISOR_REGISTRY` | `tools/drills/fixtures/registry.mjs` |
| `DRILL_SCRATCH_DIR` | where fixtures write markers |
| `SUPERVISOR_TICK_MS` | `250` — fast enough to observe, slow enough to be realistic |
| `SUPERVISOR_COMMAND_TIMEOUT_MS` | `30000` |
| `MONGODB_URI` | `''` — the harness must never touch a shared database |

On win32 `child.kill('SIGTERM')` does not run a signal handler, so the harness
asks for the drain over IPC (`{ type: 'shutdown' }`) instead. The production
`services/supervisor.mjs run` handles both paths.

## 3. The drills

| Drill | Mechanism it pins |
| --- | --- |
| `start-ready-stop` | spawn → evidence → `READY` → drain → `STOPPED`. Also the proof that the worker-evidence channel works: `drill-main` declares subscription, validated-job, outbox and freshness rules, so `READY` is unreachable without a real worker reporting them. |
| `duplicate-late-command` | the same command replayed produces **one** operation; a command that expires before it is picked up is dropped into `commands/quarantine/` with a reason instead of being executed late. |
| `socket-open-no-data` | a subscribed feed with no market event for 300 s fails the **optional** `fresh-event` rule and becomes `DEGRADED`, never `FAILED`. Missing data is not the same as a broken process. |
| `crash-restart` | the worker exits non-zero on request; the supervisor records the exit, increments `restartCount`, waits its backoff and restarts a new generation to `READY`. |
| `control-plane-restart` | the supervisor process is replaced while the worker keeps running; the new supervisor adopts the live pid and generation instead of spawning a duplicate. |
| `supervisor-restart-recovery` | a graceful drain persists `observed: STOPPED` with `desired: RUNNING` and **`restartCount: 0`**, then the next supervisor process restores `RUNNING` without a crash being recorded. |
| `reset-preserves-history` | `reset` starts a new generation and calls the module's `reset()` hook, but earlier operations and audit rows survive. |

### Why `supervisor-restart-recovery` is the strict one

This drill found two real bugs, both of which a unit test had missed:

1. **A graceful drain was counted as a crash.** The worker's `stopped` message
   arrived while the process handle was still open, so a tick re-projected the
   record as `READY`; the following exit event then looked unexpected and wrote
   `restartCount: 1`, `lastError` and a scheduled restart. The fix is a `draining`
   flag that makes `tick()` a no-op mid-drain, and a `stopped` handler that
   persists its verdict and returns instead of falling through to
   `projectRecord()`.
2. **Operator intent did not survive a supervisor restart.** `drain()` left
   `desired: RUNNING` on disk, but nothing acted on it. `reconcileDesired()` now
   queues one normal `start` per desired-RUNNING service at boot, with the actor
   `supervisor-recovery` and all the usual gates (supervised, not planned, no live
   process, no active operation).

## 4. Reading a failure

A failing drill prints the assertion, the first frames of the stack, and the tail
of the supervisor log:

```
drill crash-restart                 FAIL  7640ms
  AssertionError [ERR_ASSERTION]: restart #1 never became READY
  supervisor log (tail):
    [supervisor] host:1234 tick=250ms state=... registry=...
    2026-11-01T02:19:28.521Z [worker] drill-crash instance=si_... pid=7220 ...
```

The workspace is deleted on exit, so reproduce with a single drill and watch the
live state file if you need more:

```bash
node tools/drills/run.mjs crash-restart
```

Common causes:

| Symptom | Likely cause |
| --- | --- |
| `READY` never reached in `start-ready-stop` | the evidence channel is broken — check `services/workerProbes.mjs` / `workerHost.mjs` before the supervisor |
| `restartCount` is 1 after a clean stop | `tick()` is mutating state during a drain |
| a second worker spawned after restart | recovery not gating on the live pid / lease |
| `EPERM` in the supervisor log | atomic rename contention — `services/atomicFile.mjs` should retry it |

## 5. From drills to rollout evidence

The drills prove the **mechanism**. They do not prove a given production service
is ready to be supervised. For that, run the real service through the supervisor
and record the evidence:

```bash
node services/supervisor.mjs run          # or npm run services:supervised
node services/supervisor.mjs status
```

For a service to count as rolled out (S3 step 2) its record must show:

- `observed: READY` reached **without** `restartCount` climbing;
- every required readiness check present and passing;
- the optional `fresh-event` rule passing while the market is open, and failing
  to `DEGRADED` — never `FAILED` — while it is closed;
- `run-once` succeeding through the command inbox (not the legacy spawn-a-second-
  process path);
- the legacy orchestrator logging `[guard] SKIP <service>` for it, so there is
  exactly one owner.

Record the result in `docs/web-app/v4.2-delivery-plan.md` (§0 progress) for that
service. A rollout that cannot show this evidence is not done.

## 6. Adding a drill

1. Add the scenario as an exported `async function name(workspace)` in
   `tools/drills/run.mjs`; it must `return { detail, operationIds }` on success.
2. Register it in the `DRILLS` array — the name becomes the CLI argument.
3. Drive it only through `enqueue()` / `waitForService()` / `snapshot()` from
   `tools/drills/lib.mjs`. If a drill needs new fixture behaviour, add it to
   `tools/drills/fixtures/service.mjs` behind `TM_SERVICE_ID`, never to
   production code.
4. Keep wall-clock time bounded: the whole suite is expected to finish in well
   under a minute. Prefer `waitForService` predicates over fixed sleeps.
