## 1. The distinction that governs everything below

The repo conflates three things. V4.2 requires them to be separate:

| Layer | Definition | Count today |
| --- | --- | --- |
| **Process** | An OS process with a PID, its own event loop, its own memory ceiling | 1 (Nuxt dev server) + 1 optional (`services/run.mjs`) |
| **Service** | A registered unit of continuous work with its own lifecycle, readiness and ownership | 14 in the orchestrator + 3 embedded + 1 market plane |
| **Capability** | What the user can do; may span several services | ~20 (see `v4-product-scope-audit.md`) |

Today, **18 services run inside 1 or 2 processes**, and the most important ones
(bot supervisor, AI agent, AI review) run inside the *web* process. That is the
architectural defect §17.1 describes.

### 3.1 Behaviour of the loop

- `runOne()` calls `beat()` **before** the work (`lastRunAt`), then `lastOkAt` or
  `lastErrorAt` after. A service that hangs after `beat()` therefore looks
  "recently run" forever — the heartbeat cannot distinguish *running* from
  *stuck*. This is the core of §17.4.
- `watch()` schedules each service with a `setTimeout` chain, staggered by 3 s.
  There is no concurrency limit, no dependency ordering, and no back-pressure.
- A thrown error is caught, recorded and sent to `notify()`. The process never
  dies. A service that throws every cycle is "OK" from the OS point of view.
- `once()` runs all 14 serially and then disconnects Mongo.
- `status()` reads the heartbeat file and exits non-zero if any service is
  overdue (age > 2 × interval).

### 3.2 Heartbeat contract

`services/heartbeat.mjs` writes `node_modules/.cache/tm-trading/services.json`
(outside the dev watch path, deliberately) with this shape:

```json
{
  "updatedAt": "2026-10-31T00:00:00.000Z",
  "services": {
    "funding": {
      "intervalSec": 900,
      "lastRunAt": "...", "lastOkAt": "...", "lastErrorAt": "...",
      "lastError": null, "count": 12, "lastSummary": "{...}",
      "lastAlertAt": "..."
    }
  }
}
```

`evaluateHeartbeat()` is pure and shared by the CLI, the watch loop and the
`/health` endpoint. What it **cannot** express:

| Missing | Consequence |
| --- | --- |
| process identity (pid / host / boot id) | cannot tell "restarted" from "never ran" |
| `READY` vs `DEGRADED` vs `FAILED` | a service that connects but receives no data looks healthy |
| dependency status (Mongo, provider key) | a dead DB is reported as a service error, not a dependency error |
| data freshness per output | "ran OK" ≠ "produced new rows" |
| restart count / last restart reason | crash loops are invisible |
| queue / backlog depth | a slow consumer looks fine |
| event-loop delay, ELU, heap, GC | cannot prove the process is saturated |

`lastSummary` is a 500-character JSON slice of whatever `run()` returned — the
only per-run evidence, and it is untyped.

## 4. Embedded workers (inside the Nitro process)

| Plugin | Interval | Kill switch | What it does | Why it is a risk |
| --- | --- | --- | --- | --- |
| `server/plugins/bot-runtime.ts` | 15 s | `BOT_EMBEDDED=off` | Drives `createBotWorker` per owner with non-terminal instances or pending commands: lease, recovery, command application, one paper cycle. Nonce = `embedded-${pid}`. | Dies with the web process; a hot reload can duplicate loops; competes with HTTP for CPU |
| `server/plugins/ai-agent-runtime.ts` | 30 s | `AI_AGENT_EMBEDDED=off` | Loads `services/aiAgentWorker.mjs` and ticks the autonomous agent heartbeat/proposal cycle | Same; plus it calls external AI providers from the request process |
| `server/plugins/ai-review-runtime.ts` | 300 s | `AI_REVIEW_EMBEDDED=off` | Loads `services/aiReviewWorker.mjs` and ticks the review cycle | Same |

Both AI plugins use `pathToFileURL(join(process.cwd(), 'services', ...))` with a
`?t=Date.now()` cache-buster, so they re-import the module on every load. They are
Nitro plugins: they run once per server instance, including every dev reload.

`server/plugins/process-guard.ts` is **not** a service. It is a resilience
guard for the web process (socket teardown vs genuine rejection) and must stay.

`server/plugins/evidence-backfill.ts` and `server/plugins/news-registry.ts` are
bootstrap/migration hooks, not continuous services.

**Migration rule (§17.5, A1):** do not delete these plugins first. Move each
service to a standalone process, verify it, then flip the kill switch. The kill
switches already exist — use them as the cutover mechanism.

## 5. Market plane (event-driven, not a periodic service)

`market/index.mjs` assembles one provider into a plane:

```
provider events -> monitor -> quote/orderbook/ticker24 stores
                -> candle builder (source='trades') or 1m->4m/10m aggregator (source='kline')
                -> event bus (WS / UI / persistence)
```

Files: `market/events.mjs`, `market/clock.mjs`, `market/eventBus.mjs`,
`market/monitor.mjs`, `market/quoteStore.mjs`, `market/orderbookStore.mjs`,
`market/candleBuilder.mjs`, `market/aggregate.mjs`, `market/depthSync.mjs`,
`market/feedRecorder.mjs`, `market/healthSnapshot.mjs`, `market/quality.mjs`,
`market/reconcile.mjs`, `market/crossScanner.mjs`, `market/ticker24Poll.mjs`.

Characteristics:

- **State is in memory** (quotes, order book, ticker24). A process restart loses
  it; there is no warm-up gate before the UI renders.
- It is **lazy**: `server/utils/market-plane.ts` creates the plane on first use,
  so "market plane running" is a function of traffic, not of a lifecycle event.
- The provider is Binance-first. `market/providers/` holds the adapter contract.
- Candle persistence is a side effect of the plane, not a service. If the plane
  is never started, no candles are recorded.

In V4.2 the market plane becomes its **own process** (Market Worker) with an
explicit `READY` that means "provider connected + subscribed + first valid event
received", which is exactly the gate the UI lacks today.

## 6. Delivery path (notify + Telegram)

```
service / alert rule
  -> notify/service.mjs  notify(event, { dedupeWindowMs })
     -> notify/router.mjs   (preset, priority, dedupe key)
        -> notify/send.mjs  dispatch to sinks
           -> telegramSink -> services/telegram.mjs sendTelegram(text, tag)
           -> notification_logs (Mongo) — one row per attempt
```

Observed properties:

- `sendTelegram()` returns a **boolean**. There is no message id, no retry, no
  backoff, no delivery state machine, and no per-destination record.
- `notification_logs` records the attempt, and `dedupeWindowMs` suppresses
  repeats, but a failed send is terminal.
- Web Push / Electron sinks are injectable but unconfigured by default; an
  unconfigured channel is logged as `{ ok: false, error: 'sink not configured' }`
  rather than silently succeeding (good).
- There is **no outbox**. §7.3 requires queued → sent → delivered/failed with
  retry; today the send happens inline inside whatever service triggered it, so a
  Telegram outage slows the service loop and loses the message.

## 8. Ownership matrix (who may start/stop what)

§17.6 and §17.12 require an explicit scope for every control action. Today only
`alert_rules` and `signals` are owner-scoped; everything else is global.

| Service | Scope key | May a non-admin start/stop it? |
| --- | --- | --- |
| market plane | system | no |
| funding, scanner, news, regime, liquidation, confluence | system | no |
| brief, retention, reconcile, crossScan, macro, newsExtract | system | no |
| alertRules | `ownerId` | no (rules are per-owner, the evaluator is system) |
| signals | `ownerId` | no |
| bot instances | `ownerId` + `instanceId` | yes — the owner may start/stop their own instance |
| ai agent | `ownerId` + `agentId` | yes, within their agents |
| ai review | system | no |

This matrix is the input for the supervisor's `scopeKey` field: a control command
carries `{ serviceId, action, scopeKey, operationId }`, and the supervisor
rejects a command whose `scopeKey` the caller does not own.

## 10. Target process grouping (3–5 processes, 18 services)

Per the user's architecture review and §17.5: group by failure domain, not by
file.

| Process | Hosts | Why grouped |
| --- | --- | --- |
| **web / control plane** | Nuxt HTTP, API, SSE, Operations control endpoints | must stay responsive; never runs a work loop |
| **market** | market plane, candle persistence, liq collector | latency-sensitive, high event rate, stateful in memory |
| **intelligence** | funding, scanner, news, regime, liquidation, confluence, macro, crossScan, reconcile, retention, newsExtract | I/O-bound periodic ingestion, shared Mongo write path |
| **signals & alerts** | signalProducer, alertRules, notify/outbox | must survive an AI or market crash; owns delivery |
| **ai** | ai agent, ai review, brief | external provider calls, budget-capped, crash-isolated |
| **bots** | bot supervisor + worker per instance | owner-scoped, lease-based, must not share a lease with the web process |

Six processes is still within the "3–5, split when measured" guidance once the
AI and bot planes are counted separately — they have different failure and
authority models, so merging them would recreate the current coupling.

## 11. Registry, readiness and telemetry (S1.2)

S1.2 turns the table above into code. Three modules now describe a service
instead of inferring it from a heartbeat file, and they are deliberately
separate so each can be tested without a running process:

| Module | Responsibility | Key exports |
| --- | --- | --- |
| `services/registry.mjs` | One definition per unit of work: category, scope, execution mode, process group, entry, interval, dependencies, readiness rules, supported actions | `SERVICES`, `SERVICE_BY_ID`, `validateRegistry`, `resolveStartOrder`, `dependenciesOf` |
| `services/readiness.mjs` | Pure evaluation of the tri-state evidence the supervisor will collect | `READINESS_RULES`, `evaluateReadiness`, `deriveObservedState`, `deriveServiceHealth`, `isDrifted` |
| `services/telemetry.mjs` | Per-process saturation sampling (A7) plus a pure verdict | `createTelemetrySampler`, `evaluateTelemetry`, `explainTelemetry`, `TELEMETRY_THRESHOLDS` |

The shared contract lives in `shared/types/service.ts`:
`ManagedServiceDefinition`, `DesiredServiceState`, `ObservedServiceState`,
`ServiceHealth`, `ServiceOperation`, `ServiceReadinessCheck`,
`ServiceStateSnapshot` and `ProcessTelemetry`.

### 11.1 Registry scope

The registry declares **21** entries: the 18 services that already run plus
three planned target entries (`market-feeds`, `outlook`, `demo-runner`) marked
`planned: true`. A planned entry has no `entry` file and no control code; it
exists so the dependency graph and the Operations table can be designed before
implementation.

Two axes stay independent:

- `scope` is **data ownership** (`system`, `owner`, `account`, `session`);
- `processGroup` is **hosting** (`web`, `market`, `intelligence`, `signals`,
  `ai`, `bots`) and matches section 10.

Intervals mirror `DEFAULT_INTERVALS` in `services/heartbeat.mjs` as literals.
The registry is a definition, not an environment snapshot; the duplication
disappears when `services/run.mjs` moves onto the registry in S2.

`validateRegistry()` rejects a bad registry instead of ignoring it: duplicate
ids, unknown/self dependencies, cycles, invalid enums, invalid dependency
policies, unknown readiness rules, a periodic service without an interval, an
event-driven service with one, and a zero startup grace.
`resolveStartOrder()` is deterministic (ties keep the supplied order) and
reports unknown ids and cycles rather than returning a partial order silently.
`dependenciesOf()` is cycle-safe and never reports a service as its own
dependency.

### 11.2 Readiness semantics

Ten rules are defined. Every rule returns `true`, `false` or `null`, and `null`
means **not observed** — which is not a pass:

| Rule | Required when | Evidence |
| --- | --- | --- |
| `process-alive` | always | pid/host alive |
| `dependency-reachable` | services with dependencies | Mongo, provider, peer service |
| `subscription-acked` | exchange feeds | provider ack |
| `fresh-event` | market plane / feeds | last event timestamp |
| `recent-success` | periodic services | last completed cycle timestamp |
| `output-produced` | optional on writers | rows produced by the last cycle |
| `capability-verified` | AI / extraction | provider capability probe |
| `validated-job` | AI workers | last job passed validation |
| `outbox-consuming` | alert delivery | last outbox consumption timestamp |
| `sink-writable` | retention / reconcile | output sink writable |

Rules of the model:

- a **required** rule with `null` blocks `READY`;
- an **optional** rule with `null` never downgrades (absence of evidence is not
  a fault);
- an **optional** rule that is `false` downgrades a ready service to `DEGRADED`;
- `recent-success` defaults to `2 × interval`, with a 60 s floor;
- `STARTING` is bounded by `startupGraceMs`, after which it becomes `FAILED`;
- `UNKNOWN` counts as drift in both directions, so the supervisor reconciles
  instead of assuming the operator's intent was honoured.

### 11.3 Telemetry semantics

`createTelemetrySampler()` samples one process and releases its resources with
an idempotent `stop()`:

- event-loop delay p50/p95/p99/max from `monitorEventLoopDelay`, reset after
  every sample so a snapshot describes the window since the previous one;
- event-loop utilization delta from `performance.eventLoopUtilization`;
- heap used/total and RSS from `process.memoryUsage`;
- CPU percent over the sampling window (`null` on the first sample, because
  there is no window yet);
- GC count/total/max pause from a `PerformanceObserver` (`null` when no
  collection ran in the window).

`evaluateTelemetry()` returns `ok | elevated | saturated | unknown`, and
`explainTelemetry()` adds English reason ids (`event-loop-delay-high`,
`heap-pressure`, `gc-pause-critical`, …) for the UI to translate. A snapshot
without event-loop evidence is `unknown`, never `ok`.

## 12. Supervisor, worker host and durable commands (S1.3)

S1.3 gives the registry an executor. Four modules turn "is it running?" from a
file-age guess into a lifecycle the Operations screen can trust:

| Module | Responsibility | Key exports |
| --- | --- | --- |
| `services/supervisorStore.mjs` | Durable state: desired/observed per service, operations, idempotency keys, leases, bounded audit | `createSupervisorStore`, `serviceKey`, `SUPERVISOR_STATE_FILE`, `readStateFile` |
| `services/supervisor.mjs` | The single owner of lifecycle: validate a request, advance operations on `tick()`, reconcile processes, drain and adopt | `createSupervisor`, `createProcessAdapter`, `SERVICE_ACTIONS`, `restartBackoffMs` |
| `services/workerHost.mjs` | One child process per service instance: cycle loop, heartbeat, telemetry, drain, one-shot mode | `createWorker`, `runCycle`, `cycleIntervalMs` |
| `services/workerProbes.mjs` | The evidence a worker is allowed to claim, collected from things it can actually observe | `outputCountOf`, `cycleSucceeded`, `probeProviderCapability`, `probeSink`, `mongoEvidence` |

### 12.1 Why a file store, and not Mongo, in S1.3

The supervisor is a **single process on one host** (`nssm`/Task Scheduler on
win32, `systemd` on Linux). A JSON file written atomically is durable across
supervisor restarts, needs no connection at boot, and lets the supervisor stop
a wedged service **even when Mongo is down** — which is exactly when an
operator needs it most. Every mutation is written to disk before the caller is
acknowledged. The Mongo adapter arrives in S2, when the HTTP API and the
supervisor become separate writers and need real multi-writer semantics.
`file: null` yields an in-memory store with identical behaviour, so the tests
exercise the real code path without touching disk.

### 12.2 Operation semantics

- `request()` validates action/actor/idempotency key, persists the operation
  **before** returning, and returns the persisted record. A repeated
  idempotency key resolves to the same operation; the same key with a different
  action is a mismatch, never a silent replay; a second command for a busy
  service is refused with the active operation.
- `tick()` expires leases, expires timed-out operations, reconciles process
  state, then advances every active operation. Nothing is spawned by
  `request()`.
- **START is not done when `spawn` returns.** It stays `RUNNING` with a phase
  (`starting`, `awaiting-dependency`, `awaiting-readiness`) until readiness is
  proven, then completes. A worker that never proves readiness is failed with
  `READINESS_TIMEOUT` and killed.
- **STOP drains via an IPC `shutdown` message** and only escalates to `SIGKILL`
  after the grace period, recording the escalation. `child.kill('SIGTERM')` is
  not a graceful stop on win32, so it is a fallback, not the mechanism.
- **RESTART/RESET** drain the current generation and start a new one; the
  operation records the previous `serviceInstanceId` and bumps `generation`.
  `reset` additionally asks the module for an optional `reset()` hook and never
  deletes history.
- An **unexpected exit** is `FAILED` with a bounded-backoff restart
  (`restartBackoffMs`: 2 s, 4 s, 8 s … capped at 60 s) and an audit row.
- A service that another process still hosts (`supervised: false`) and a
  `planned: true` service may only be **probed**; `request()` rejects every
  other action so the supervisor can never duplicate processing.

### 12.3 Worker evidence and honesty rules

The worker reports tri-state evidence; `null` means **not observed** and is
never treated as a pass by `services/readiness.mjs`:

- `dependenciesReachable` — a configured dependency answered (Mongo ping), or
  the service has no external dependency to reach;
- `sinkWritable` — Mongo when it is the store, otherwise a real `access(W_OK)`
  on the data directory;
- `capabilityVerified` — a **free** provider probe (`GET /models`,
  `GET /api/tags`) that never spends tokens; an unconfigured provider is
  `null`, a rejected credential is `false`;
- `lastOutputCount` — rows the last completed cycle reported.

Two rules keep the evidence honest:

- **a skip is not a success**: a cycle that reports `skipped` keeps
  `lastSuccessAt` and `lastOutputCount` untouched, so "outside the brief window"
  cannot mask a broken brief;
- **a throw is a failed cycle, not a dead worker**: the loop reports the error
  and tries again on the next tick.

### 12.5 CLI (the first control path)

Until the S2 HTTP API exists, the supervisor is driven from the CLI:

```bash
node services/supervisor.mjs status              # adopt + tick + print the table
node services/supervisor.mjs tick                # one reconciliation pass
node services/supervisor.mjs run                 # supervisor loop (SUPERVISOR_TICK_MS)
node services/supervisor.mjs start news --actor=ops --reason="pilot"
```

`run-once` and `reprobe` are real operations here: `run-once` either dispatches
to the running worker or forks a one-shot worker that reports its result, and a
detached spawn reported as success — the anti-pattern in
`docs/web-app/v4.2-operations-control-audit.md` — is not possible.

**Not wired yet:** `services/run.mjs` still owns its own list and the Nitro
plugins still host the embedded workers, so no service is yet started by the
supervisor in production. Wiring `run.mjs` onto the supervisor, the Operations
API and the UI is S2/S3.

| `server/api/v1/operations/operations/[operationId].get.ts` | Poll one operation until it is terminal |
| `tests/operations-view.test.ts` | Merge rules: never-started is not an error, drift needs expressed intent, tracked-but-unregistered rows survive, operations are newest-first |

### 13.1 Why a command inbox (option b)

The supervisor is the **single writer** of service state, and it is a separate
process. If the API wrote state too, two writers would race on one record. So the
API never runs the supervisor: it mints an `operationId`, drops a command in the
inbox, and the supervisor performs it on its next tick.

- one file per command, written tmp+rename, so concurrent API workers cannot
  corrupt a shared array and a partial command is never observed;
- delivery is **at-least-once**, which is safe because the supervisor's
  `request()` is idempotent on the caller-minted `operationId` — replaying a
  command resolves to the same operation, not a second one;
- a command is only removed once it has been performed, was permanently invalid,
  or expired. A **busy service defers** it to a later tick rather than dropping
  it;
- every rejection, expiry and unreadable file leaves an audit row, so nothing is
  dropped silently;
- `node services/supervisor.mjs status` does **not** consume the inbox: a read
  command must never start a service.

The async contract is explicit: `POST` returns `202` with an `operationId`, and
the caller polls `statusUrl` until the state is `SUCCEEDED`, `FAILED` or
`UNCONFIRMED` — "command accepted" is never reported as "process started".

Rules encoded:

- **never-started is not "stopped on purpose"**: a registry entry with no state
  is `registered: false, observed: 'UNKNOWN'`, so the table cannot claim a
  deliberate stop it never observed;
- **drift needs intent**: an untouched service is not drifting; a service whose
  operator intent cannot be proven is;
- **nothing tracked is dropped**: a snapshot record the registry does not know
  still appears, because it is a real process;
- **reads are not root-only**: any authenticated user may read status; only
  mutations (start/stop/restart/reset/probe/run-once) are privileged.

### 13.2 UI on the existing route (S2, step 3)

The control plane is mounted on the **existing** `/operations` page, so no new Hub
route and no seed is required:

| Module | Responsibility |
| --- | --- |
| `shared/types/operations.ts` | The read model and command/status envelopes the app and the API share |
| `app/composables/useOperations.ts` | `view()` / `command()` / `operation()` |
| `app/components/operations/ServicesPanel.vue` | Summary + filters + the service table (`LazyGridList`) with list/grid views, grouped context menu, swipe shortcuts, drag reorder and a bounded scroll area |
| `app/components/operations/ServiceDetailDrawer.vue` | Lazy drawer: overview, readiness checks, workload, A7 telemetry, activity and audit |
| `app/components/operations/ServiceActionButton.vue` | One operation, surface → poll → terminal result, with the live phase shown |
| `app/utils/serviceActions.ts` | The one place that decides an action's icon, colour and whether it is allowed |
| `app/utils/serviceOperation.ts` | The shared follow-to-terminal loop (injected transport, no leaked timer) |
| `tests/operations-ui.test.ts` | Wiring pins: default tab, mobile slot, lazy drawer, list/grid, context menu, drag, scroll, "accepted ≠ succeeded" |
| `tests/service-actions.test.ts` | Action availability rules and the operation loop (timeout → UNCONFIRMED, abort → CANCELLED) |
| `tests/operations-i18n.test.ts` | Closed sets for every dynamic key (service labels, states, actions, phases, audit, rules), derived from the registry and the supervisor source |

Rules encoded:

- the table is a **read model**: the row body never mutates, every action lives in
  the drawer, so a mis-click cannot start or stop anything;
- **accepted is not succeeded**: the button shows the phase (starting,
  awaiting-readiness, draining …) and only reports an outcome once the operation
  is terminal; `UNCONFIRMED` is presented as "check by hand", never as success;
- a service that is `planned` or hosted by another process has every action but
  `probe` disabled;
- service labels are translated by id, so a Vietnamese screen never shows an
  English registry label;
- the row list follows the repository `LazyGridList` standard: **list and grid**
  views (persisted per user), a **grouped, colour-coded context menu** (long-press
  on mobile, `⋯` on desktop), a dedicated mobile card, **swipe shortcuts**, and
  **drag to reorder** (persisted per user, disabled while filtering). The list has
  a **bounded height with its own scroll area** so a 21-row registry never pushes
  the rest of the screen away;
- whether an action is allowed is decided in **one place**
  (`app/utils/serviceActions.ts`), and the follow-to-terminal loop in
  `app/utils/serviceOperation.ts` is shared by the row button, the context menu
  and the swipe shortcuts — so no surface can report a different outcome.

### 13.3 Live stream (S2, step 4)

| Module | Responsibility |
| --- | --- |
| `server/utils/operationsStream.ts` | Pure protocol helpers: `sseFrame()` (newline-safe) and `operationsSignature()` (what the screen renders) |
| `server/api/v1/operations/events.get.ts` | `GET /api/v1/operations/events` — `text/event-stream`, polls the state every 2 s, emits only on change, pings every 15 s |
| `shared/utils/operationsStream.ts` | `parseOperationsSseFrame()` — spec-correct frame decoding |
| `app/composables/useOperationsEvents.ts` | `fetch` + ReadableStream reader (not `EventSource`), bounded-backoff reconnect |

Why poll-and-push instead of a push bus: the supervisor is a **separate process**,
so it cannot write into the web server's memory. The endpoint polls the same
state the REST read serves and emits a `snapshot` only when the fingerprint
changes, so a 2 s poll does not become 30 identical events a minute. Because the
first event is always the current snapshot, a reconnect needs no separate REST
reconcile, and the table falls back to its 15 s poll while the stream is down.

`EventSource` cannot send an `Authorization` header, so the client reads the
stream with `fetch` and the Bearer token the app already uses.

## 14. Rollout guard (S3, step 1)

S3 moves the 14 periodic services off the legacy in-process orchestrator
(`npm run services`) and onto the supervisor. The one thing S3 must never do is
run both for the same service: two copies of a producer means duplicate Telegram
alerts, duplicate intel writes and wasted provider budget (§17.15-O4).

`services/orchestratorGuard.mjs` is the mechanism. It is **read-only and pure**:

| Rule | Why |
| --- | --- |
| A **live** supervisor lease blocks the service | The supervisor is the authority on who is running what |
| An **expired** lease blocks nothing | A crashed supervisor releases nothing, so it must not lock the orchestrator out forever |
| Only the same `scopeKey` counts | Ownership scope is part of the service identity |
| The orchestrator's own owner id is ignored | The guard must never block itself |
| A missing/broken store degrades to "run everything" | A guard that stops all work when a cache file is unreadable is worse than the overlap it prevents |

`services/run.mjs` consults it at start and **re-checks every cycle** in `watch`
(a supervisor may adopt a service after the orchestrator has started), skips the
owned ones with a log line, and exits non-zero from `once` when it ran nothing.
Two escape hatches exist for a deliberate override:

- `SERVICES_ALLOW_OVERLAP=1` — run anyway, loudly (duplicate work is intentional);
- `TM_SUPERVISOR_STATE` — point the guard at a different state file.

New entry points (package.json): `npm run services:supervised` runs the supervisor
loop, `npm run services:supervisor:status` prints its table. The legacy
`npm run services` still works, but now refuses to touch a supervised service.

`tests/orchestrator-guard.test.ts` pins each rule, plus the supervisor side of the
contract (`OPERATION_IN_PROGRESS`, `LEASE_HELD`).

### S3 step 2 — the guard is only as good as the lease

The rollout run (see `v4.2-delivery-plan.md` §S3) found that the supervisor claimed a
lease at spawn and **never renewed it**. With a 30 s TTL, a running service silently
lost its claim half a minute after every start and the guard then reported
`0 blocked / 14 runnable` while 13 services were supervised — the overlap this section
exists to prevent, with the guard looking healthy.

`renewHostedLeases(at)` in `services/supervisor.mjs` now refreshes the lease for every
instance the process hosts on each tick (and takes over a previously owned claim once
it has expired, so an adopted instance from a restarted supervisor converges). A lease
still held by another live owner is left alone. The regression test is
`the lease is renewed while the instance is alive, so the guard keeps blocking`.

`node services/run.mjs plan` prints the split (`[guard] SKIP …` per owned service) and
runs nothing, which is the safe way to inspect the guard on a machine with a live
supervisor.

### Who drives the loop

Three ways to host the supervisor, in increasing order of isolation:

| Host | Command | Use for |
| --- | --- | --- |
| CLI daemon | `npm run services:supervised` | a local operator session; dies with the terminal |
| Embedded driver | nothing — `server/plugins/service-supervisor.ts`, on by default | dev and single-process self-hosting, so the dashboard is honest without a second terminal |
| OS service | your process manager, with `SERVICE_SUPERVISOR_EMBEDDED=off` | anything beyond one box |

The embedded driver is the same `createSupervisor` the other two use; it adopts existing
pids and reconciles `desired` on boot, then ticks every `SERVICE_SUPERVISOR_INTERVAL`
(default 5 s, min 2 s). Two escape hatches, because a web process must never be the only
thing holding the services up:

- `SERVICE_SUPERVISOR_EMBEDDED=off` — do not drive the loop from Nitro at all (run it as
  an OS service instead);
- `SERVICE_SUPERVISOR_AUTOSTART=off` — drive the loop, but never queue the first start
  for an untouched state file.

It auto-starts exactly the services it owns (`server/utils/embeddedServices.ts`): the 13
periodic ones, never a service another process hosts (`supervised: false`), never a
`planned` stub, and never `retention` — that purges data by policy, which is an operator
decision. Its `close` hook stops the tick timer and **nothing else**: a Nitro restart is
a control-plane restart, and the next boot adopts the same worker pids
(`[... adopted=13 recovered=0 autostart=0 ...]`).

### The other half of a control-plane restart

Adoption only works if the worker is still there. `services/workerHost.mjs` used to die
on the restart: `process.send()` on a closed channel emits `error` on `process` rather
than throwing, and nothing listened, so the next heartbeat became
`uncaughtException: ERR_IPC_CHANNEL_CLOSED`. It now sends with a callback and listens for
`ERR_IPC*`, logs `lost its control-plane channel` once, and stays up for
`WORKER_CHANNEL_GRACE_MS` (default 5 min) so the next supervisor can adopt the pid;
nothing adopting it means a clean exit 0. Contract pinned by
`tests/worker-channel.test.ts`.

## 15. Service objectives (SLOs, S9)

`services/slo.mjs` turns §17.13 into three objectives per service, each fed by
evidence the supervisor already records:

| Objective | Evidence | Triage |
| --- | --- | --- |
| `freshness` | `lastSuccessAt`, `intervalSec` | budget `3 × interval` (300 s floor); late at ≤ 2×, breached beyond |
| `flapping` | `crash-restart` / `worker-exited` audit rows, last hour | warn 2, breach 4 |
| `saturation` | the A7 telemetry sample | mirrors the telemetry verdict |

`evaluateSlo()` returns `{ schemaVersion, status, objectives[] }` with
`status ∈ { ok, at-risk, breached, unknown }`; the service verdict is the worst
objective. Two rules keep it honest rather than decorative:

- **No duty means no SLO.** A service the operator has not asked to run
  (`desired !== 'RUNNING'`, or an unknown service) has every objective `unknown`.
  A never-started service is **not** a green `ok`.
- **`unknown` is never a pass.** An objective with no evidence (no completed
  cycle, no telemetry) is `unknown`, and the roll-up counts it separately in
  `summary.sloUnknown` instead of folding it into `ok`.

`services/operationsView.mjs` merges the verdict onto every row and rolls up
`sloBreached` / `sloAtRisk` / `sloUnknown`. The UI renders it as a badge column,
a header roll-up and a per-objective list in the drawer
(`app/components/operations/ServiceSloBadge.vue`); the objectives and statuses are
translated (`operations.services.slo.*`). Deliberately **not** modelled:
availability percentage and error rate — they need a request/uptime time series
this system does not record, and D12 forbids reporting a number we cannot measure.

`tests/slo.test.ts` pins the triage boundaries, the no-duty rule, the telemetry
mirror, the worst-objective composition and the read-model roll-up.

## 16. Control-plane latency (S9)

§17.13 also asks for startup/stop latency. It is derived, not sampled: for each
service, `services/operationsView.mjs` times the latest **terminal** operation
(`SUCCEEDED` / `FAILED` / `CANCELLED` / `UNCONFIRMED`) and exposes it as
`control`:

| Field | Meaning |
| --- | --- |
| `queueMs` | requested → started: how long the command waited in the inbox |
| `runMs` | started → finished: how long the supervisor spent |
| `durationMs` | requested → finished: the total a person waited |

An in-flight operation has no finish, so the service carries **no** control metric
(`control: null`) rather than a zero, and a half that never happened (no start) is
`null` and renders as `—`. The metric is read from the whole timeline, not the
capped `operations` slice, so a service keeps its last measured value after it
falls out of the recent list. The drawer renders it under "Control plane"
(`app/components/operations/ServiceDetailDrawer.vue`); `tests/operations-view.test.ts`
pins the split, the null cases, the newest-wins rule and the slice-independence.

## 17. Dead-letter quarantine (S9)

A command the supervisor will never perform — rejected, expired, or unparseable —
used to be deleted, leaving "nothing happened" with no explanation. §17.11 requires
a dead-letter/quarantine, so `services/commandInbox.mjs` now provides:

| Function | Purpose |
| --- | --- |
| `quarantineCommand(command, { reason })` | move a dropped command to `commands/quarantine/` with the reason, remove the original |
| `quarantineFile(file, { reason })` | preserve an unparseable file's raw bytes verbatim, then remove it from the inbox |
| `listQuarantine()` | newest-first view for the operator |
| `quarantineCount()` | cheap count for the status screen (directory only, no parse) |
| `pruneQuarantine()` | keep the newest `DEFAULT_MAX_QUARANTINE` (100), so the box cannot become a second outage |

`services/supervisor.mjs` routes all three drop paths through it (`command-rejected`,
`command-expired`, `command-invalid`), still audits each one, and exposes
`node services/supervisor.mjs quarantine` to list the box. The original command file
is always removed, so a command the supervisor has given up on can never be retried
by a later tick. `loadOperationsView` adds the count to the summary as
`deadLetterCount` (§17.13 "dead-letter count") and the Services header shows a badge
when it is non-zero, so a silent queue can never look healthy. Runbook `§9a`
(`docs/user-guide/runbooks.md`) explains how to act on each reason;
`tests/failure-drills.test.ts` pins the move, the raw-byte preservation, the bound,
the count and the "no longer pending" rule.
