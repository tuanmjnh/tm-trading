## 1. Scope split

V4.2 contains two workstreams that must not be mixed into one big-bang rewrite:

| Track | Source | Outcome |
| --- | --- | --- |
| **T — Reliability** | §17 (authoritative, mandatory) | Every background service is a registered, observable, controllable resource; `/operations` is a truthful control plane. |
| **P — Product** | §0–16 (V4.0/V4.1 carry-forward) | Five compact workspaces (Overview, Discover, Watchlist & Signals, Intelligence, Alerts) over one shared evidence/data layer, plus Advanced/Research and Platform & Administration groups. |

Hard rules carried from the roadmap:

1. `command accepted ≠ process started ≠ service ready ≠ doing useful work`.
2. One vertical slice at a time, demonstrated on real source data.
3. Nothing is marked implemented without passing tests + runtime evidence.
4. TM Hub stays the owner of identity, RBAC, app registry, route registry and shared core.
5. No MT5/Exness/Forex/EA scope; demo execution only.

## 4. Decisions to confirm before coding (ADR-required)

| # | Decision | Recommendation |
| --- | --- | --- |
| A1 | **Who owns continuous work?** | A dedicated `node services/supervisor.mjs` process (external to Nuxt), with `DEVELOPMENT_EMBEDDED` mode only behind an explicit flag. The OS wrapper never replaces the supervisor: systemd on Linux, a Windows Service wrapper (nssm) or Task Scheduler on win32, Docker Compose if containerised. PM2 is Linux-oriented and should not be the primary choice on this win32 workstation. |
| A2 | **Where does service state live?** | Mongo collections `service_definitions`, `service_state`, `service_operations`, `service_events`; keep `logs/services.json` as a *derived* projection so `/health` and `npm run services:status` keep working during migration. |
| A3 | **Control transport** | REST commands (`202 + operationId`) + authenticated SSE `/api/v1/operations/events`, REST snapshot for recovery. Reuse the existing SSE plumbing if it meets auth/ordering; do not add a second stream. |
| A4 | **Navigation source of truth** | Keep the Hub route registry. Workspace routes are registered through `tm-hub` seed (`pnpm seed --app=trading`); old paths become redirects/aliases, not deletions. |
| A5 | **Queue technology** | No Redis/BullMQ now. A Mongo lease + outbox with exponential backoff already exists as a pattern (`trading_domain_events`, Phase C); BullMQ needs Redis (awkward on win32) and would be a *second* queue beside it. Adopt only with measured backlog/latency evidence, and replace rather than duplicate the Mongo outbox. |
| A6 | **AI gateway sequencing** | Finish Phase G (task profiles + real second provider) before evidence packets and outlooks, otherwise the outlook contract has no verified router behind it. |
| A7 | **Per-process runtime telemetry** | Each worker reports `perf_hooks.monitorEventLoopDelay()` p95/p99, `eventLoopUtilization()`, heap/RSS, CPU and GC pause over the control channel; Operations renders them per service. This is additive to §17.13, not a replacement. |

Open question for the product owner: **does Track T ship before Track P**, or do they run interleaved?
This plan assumes interleaved with T first in each wave (see §9), because §17 is marked mandatory.

- **shared/types/service.ts** (new) — `ManagedServiceDefinition`, `DesiredServiceState`, `ObservedServiceState`,

- Per-service readiness policies (exchange feed = subscription ack + fresh event; scanner = recent completed
  cycle + output count; news = successful fetch cycle; AI = capability check + validated job; Telegram = bot identity

- Dependency graph validation (cycle rejection) + dependency policy `REQUIRE_READY | DEGRADED_ALLOWED | OPTIONAL`.
- Mongo models + indexes; migration keeps the JSON heartbeat as a read-only projection.
- Per-process telemetry (A7): event loop delay p95/p99, ELU, heap/RSS, CPU, GC pause — sampled in each worker

**S1.3 Supervisor + durable commands** (§17.5–17.6)

- **services/supervisor.mjs** (new) — one authoritative process: claim lease, spawn/adopt workers, heartbeat sequence,

- **services/supervisorStore.mjs** (new) — persist command before ack, `operationId` + idempotency key, serialization of

- Windows note: `child.kill('SIGTERM')` is not graceful on win32 — drain must use an IPC `shutdown` message with a
  timeout fallback. This is a first-class test case, not a footnote.
- `reset` policies per service, default = restart + reinitialize ephemeral state; never delete history.

Exit criteria: unit/integration tests for start→ready, stop→drained, restart→new instance, duplicate command
serialization, expired lease, supervisor restart.

### S3 — Roll out remaining services · delivered

**Step 1 (done): the overlap guard.** `services/orchestratorGuard.mjs` + the wiring in
`services/run.mjs` make "never run legacy and supervised consumers simultaneously"
machine-enforced instead of a note: `npm run services` now skips (and logs) any
service a live supervisor holds, re-checking every cycle, and exits non-zero from
`once` when it ran nothing. `npm run services:supervised` starts the supervisor loop.
See `v4.2-service-inventory.md` §14.

**Step 2 (done): the per-service rollout.** Every supervised periodic service
(`funding`, `scanner`, `news`, `regime`, `liquidation`, `confluence`, `crossScan`,
`macro`, `newsExtract`, `reconcile`, `alertRules`, `signals`, `brief`) was started
through the supervisor's command inbox against the real registry and real providers,
and reached the acceptance bar: `observed: READY` (11) or `DEGRADED` on the optional
`output-produced` rule only (`news`, `liquidation`), every required readiness check
passing, all 13 starts delivered through the durable command inbox (`enqueueCommand`
→ daemon), `run-once` succeeding via the supervisor CLI (`funding`: 822 rows checked,
`mongo: up`, 15 s), and one `[guard] SKIP <service>` per supervised service from the
legacy orchestrator.

Three defects were found and fixed by that run — they are written up as R1–R3 in
`v4.2-operations-control-audit.md` §7.1:

- leases were claimed at spawn and **never renewed**, so the overlap guard stopped
  seeing a live supervisor ~30 s after every start (R1, high);
- a dependency in `FAILED` with `desired: RUNNING` was a **hard block** instead of a
  wait, which made batch cold starts and supervisor restarts fail dependents (R2, high);
- `signals` was gated on `market-plane`, which is hosted in the Nitro process
  (`supervised: false`) and can never be observed READY, so the signal producer could
  not start at all (R3, high).

`retention` is deliberately not started: it purges rows past their declared
retention window, which is an operator decision, not something a rollout run should
do. Its guard behaviour is identical.

`node services/run.mjs plan` was added for this evidence: it prints the same
`[guard] SKIP` lines `once` would print and exits without running anything, so the
split is inspectable on a machine where a supervisor is live.

**SLOs done.** `services/slo.mjs` defines exactly three objectives, each fed by
evidence the supervisor already records, because an SLO that cannot be measured is
a number nobody can trust:

| Objective | Input | Verdict |
| --- | --- | --- |
| freshness | `lastSuccessAt` and `3 × interval` (300 s floor) | `ok` inside budget, `at-risk` at ≤ 2×, `breached` beyond |
| flapping | `crash-restart` / `worker-exited` audit rows in the last hour | `ok` < 2, `at-risk` ≥ 2, `breached` ≥ 4 |
| saturation | the A7 telemetry verdict | mirrors `ok` / `elevated` / `saturated` |

Two honesty rules are load-bearing: a service the operator never asked to run has
**no duty**, so its verdict is `unknown` (never a green `ok` for a service that has
never met anything), and `unknown` is a first-class verdict that is never folded
into a pass. The service verdict is the worst objective. The read model merges the
verdict onto every row and rolls up `sloBreached` / `sloAtRisk` / `sloUnknown` in
the summary, so a badge can never disagree with the table. The UI shows it as a
badge column, a header roll-up and a per-objective list in the drawer
(`app/components/operations/ServiceSloBadge.vue`). Deliberately absent:
"availability %" and "error rate", which would need a time series this system does
not record — the honesty rule (D12) forbids inventing them.

**Runbooks and drills.** Every failure mode in §17.11 now has a recovery runbook
with symptom / confirm / fix / prevent (`docs/user-guide/runbooks.md`). The drills
that are pure enough to assert without a live cluster are pinned in
`tests/failure-drills.test.ts` — bound, corrupt-item, replay and capacity drills for
the command inbox — and the bounded inbox itself was added in this stage
(`DEFAULT_MAX_PENDING`, `InboxFullError`, the command endpoint answering `429`
instead of `500`, and the batch endpoint reporting `truncated`). A queue with no
ceiling is a slow-motion outage, so the ceiling is now explicit.

**Dead-letter / quarantine done.** §17.11 also asks for dead-letter/quarantine, and
until now a dropped command was simply deleted — "nothing happened" with no
explanation. Rejected, expired and unparseable commands are now moved to
`commands/quarantine/` with the reason attached (`quarantineCommand` /
`quarantineFile` in `services/commandInbox.mjs`), the original is removed so it
cannot be retried, and the box is bounded (`DEFAULT_MAX_QUARANTINE`, oldest pruned)
so it cannot become a second outage. `node services/supervisor.mjs quarantine` lists
it (newest first), the count is surfaced in `summary.deadLetterCount` and shown as a
header badge when non-zero (§17.13 "dead-letter count"), and the runbook `§9a`
explains how to act on each reason.

**Control-plane latency done.** §17.13 also asks for startup/stop latency. Rather
than add a new timer, the read model times the operation timeline the supervisor
already records: for each service, the latest **terminal** operation is summarised
as `control: { operationId, action, state, requestedAt, startedAt, finishedAt,
durationMs, queueMs, runMs }`. `queueMs` (requested → started) is the wait for the
supervisor; `runMs` (started → finished) is the work; `durationMs` is the sum a
person felt. An in-flight operation has no finish, so it is **not** timed — the
service simply carries no control metric rather than a misleading zero, and a
missing half shows `—`. The metric is derived from the whole timeline, not the
capped `operations` slice, so an older service keeps its last measured value after
it falls out of the recent list. It is surfaced in the service drawer
(`ServiceDetailDrawer.vue`, "Control plane") and pinned in
`tests/operations-view.test.ts`.

**Live drills done.** The remaining §17.11 drills needed a running supervisor, so
`tools/drills/` provides one: each drill spawns the **real** `services/supervisor.mjs
run` process, which forks the real worker host over IPC, against a fixture registry
(`TM_SUPERVISOR_REGISTRY`, `tools/drills/fixtures/registry.mjs`) in an isolated
workspace under `node_modules/.cache/tm-trading/drills/`. Nothing is mocked and no
shared database is touched (`MONGODB_URI=''`). `npm run drills` runs all seven and
exits non-zero on failure:

| Drill | Pins |
| --- | --- |
| `start-ready-stop` | spawn → worker evidence → `READY` → drain → `STOPPED` |
| `duplicate-late-command` | one operation per replayed command; expired commands quarantined |
| `socket-open-no-data` | a subscribed feed with no ticks is `DEGRADED`, not `FAILED` |
| `crash-restart` | exit detected, backoff, new generation reaches `READY` |
| `control-plane-restart` | a new supervisor adopts a live pid/generation instead of duplicating |
| `supervisor-restart-recovery` | graceful drain keeps `desired: RUNNING`, `restartCount: 0`; the next process restores it |
| `reset-preserves-history` | reset starts a new generation, keeps operations and audit rows |

The harness earned its place by finding two bugs unit tests had missed: a clean
drain was counted as a crash (and inflated `restartCount` on every deploy), and
operator intent did not survive a supervisor restart at all. Both are fixed —
`drain()` now sets a `draining` flag that makes `tick()` a no-op, the `stopped`
handler persists and returns instead of re-projecting readiness, and
`reconcileDesired()` queues one normal `start` per desired-RUNNING service at
boot. `tests/supervisor.test.ts` covers both, and the drill asserts them end to
end. What the drills do **not** prove is that any given production service reports
its evidence correctly — that is S3 Step 2, and it needs an operator run.

See `docs/web-app/v4.2-drills.md` for isolation, env vars, failure triage and how
to add a drill.

## 8. Risks and mitigations

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Hub route registry is external (`tm-hub` seed) | New pages invisible or 404 after consolidation | Do route work as paired changes: local page + Hub seed; keep old paths as redirects; verify with a seeded local hub or the deployed hub |

| Windows process semantics | “Graceful stop” silently becomes force-kill | IPC `shutdown` + drain timeout + explicit escalation record; test on win32 |
| Heartbeat file lives in `node_modules/.cache` | State lost on clean install; single-host assumption | Mongo is the source; JSON becomes a projection written by the supervisor |
| Mongo may be absent (fail-soft app) | Operations page blank / control plane dead | Explicit `UNKNOWN`/`UNAVAILABLE` states; supervisor still runs with file-only degraded mode |
| 79 pages, many deep links | Broken links, lost permissions | Migration map + redirects + Hub route IDs preserved; hide menu entries, never delete capability |
| Legacy + supervised duplicate consumers | Duplicate alerts/orders | One service per commit; duplicate-processing check in the drill harness |
| Pine licensing/parity | Legal exposure, wrong signals | No PineTS in production before license decision + parity fixtures; unsupported scripts get an explicit report |
| Scope creep back to a trading terminal | Product drift | §0.2 / §16.17 non-goals reviewed at every stage gate |
