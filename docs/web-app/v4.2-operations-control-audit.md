## 1. What "Operations" is today

| Layer | Reality |
| --- | --- |
| Page | `app/pages/operations.vue` — header comment says "Read-only by contract (D1): every number is an API/database read, never a store blip yields an empty section instead of a stack trace" |
| Data | `GET /api/v1/health` (DB + heartbeat file), `GET /api/v1/market-sources/health`, plus bots/positions/alerts/agents read models |
| Controls | exactly two mutations: `POST /api/v1/admin/services/run-once` and `POST /api/v1/admin/health/services/reprobe` |
| State source | `node_modules/.cache/tm-trading/services.json`, written by the orchestrator, read by `loadServicesStatus()` |
| Lifecycle | none. There is no desired state, no supervisor, no start/stop/restart/reset |

The page is a **dashboard**, not a control plane. It renders what a file says. That
is honest today, but it cannot satisfy §17.9 because there is nothing to control.

## 3. The `run-once` anti-pattern, step by step

This single handler violates six of the §17.6/§17.7 rules at once. It is worth
walking through because it is the model the rest of the control plane must *not*
copy.

```
POST /api/v1/admin/services/run-once
 1. requireOwnerId(event)                       // any logged-in user
 2. spawn(process.execPath,
          ['services/run.mjs', 'once'],
          { detached: true, stdio: 'ignore',
            env: { ...process.env, OWNER_ID: ownerId } })
 3. child.unref()                               // fire and forget
 4. await sleep(800)                            // "give it a moment"
 5. services = loadServicesStatus()             // read the OLD heartbeat file
 6. return { success: true, message: 'Services execution started', data: { services } }
```

| Rule (§17.6/§17.7) | What happens | Why it matters |
| --- | --- | --- |
| "Create `operationId` and persist command" | no record exists | after a refresh there is no way to know a run was requested, or whether it finished |
| "Do not start a permanent service as a side effect" | a full `once` run executes all 14 services | acceptable for `once`, but the caller gets no job id, so it cannot be observed |
| "Return `202 Accepted` + `operationId`" | returns `200` + `success: true` | the UI treats "spawned" as "done" |
| "Require an idempotency key" | none | double-click spawns two full runs; both write `intel` snapshots (`deleteMany` + insert), so they race |
| "Create an audit record" | none | no actor/action/result trail |
| "Do not return raw command lines" | returns `ownerId` and the full service list | minor leak, but shows the response is a debug payload |

The 800 ms sleep is the tell: the handler knows the work is asynchronous, then
papers over it with a fixed delay and reports the *pre-existing* heartbeat as if
it were the result. `data.services` is almost always the state from **before**
the run.

**UI side** (`operations.vue:1096`):

```ts
async function runAllServices() {
  const result = await $fetch('/api/v1/admin/services/run-once', { method: 'POST' })
  if (result.success) {
    notify.success(t('operationsCenter.actions.successRunAllServices'))
    await loadAll()
  }
}
```

`success: true` is always true, so the toast always fires, and `loadAll()`
immediately re-reads the same stale file. The user sees "started" with no way to
see "finished".

## 4. `reprobe` is not a probe

`reprobe` re-reads the heartbeat JSON. It does not contact Mongo, a provider, or a
worker. `loadServicesStatus()` is:

```ts
const m = await heartbeatMod()
return m.evaluateHeartbeat(m.readHeartbeat(), now)
```

So `POST /reprobe` returns the same numbers as `GET /health`, with a new `now`.
The endpoint's doc comment claims it "writes fresh heartbeats to the JSON store",
which is false — it writes nothing.

§17.6 defines PROBE as: "Report dependency connectivity, capability, latency,
freshness and last successful functional result" and "must not alter desired
lifecycle state". A real probe must reach the dependency. This one does not.

## 5. State model gap

`evaluateHeartbeat()` produces exactly one boolean per service: `overdue = age >
2 × interval`. Everything else is derived in the page.

| §17.9 column | Available today | Gap |
| --- | --- | --- |
| Service name / category / id | name only | no registry, no category, no human label |
| Scope | none | no `scopeKey`; `alertRules`/`signals` are per-owner but not labelled |
| Desired | none | nothing is ever desired; services either run in a process or not |
| Observed | `overdue` boolean | no STARTING/READY/DEGRADED/STOPPING/STOPPED/FAILED/UNKNOWN |
| Health | `healthy \| degraded` at system level | not per service, not per dependency |
| Last heartbeat | `lastRunAt` / `lastOkAt` / `lastErrorAt` | no pid, host, boot id or generation |
| Last successful work | `lastOkAt` + 500-char `lastSummary` | untyped; "ran" ≠ "produced rows" |
| Data freshness | none per service | computed ad hoc in each page |
| Workload | none | no queue depth, no lag, no duration history |
| Actions | run-once (all), reprobe | no start/stop/restart/reset, no per-service run-once |

Concretely, these two states are indistinguishable today:

- service is running, connected, and producing rows;
- service crashed at boot, `beat()` recorded `lastRunAt`, then the process died.

Both render as "OK" until 2 × interval elapses, and after that both render "DEAD".

## 6. Nuxt coupling

Three continuous loops live inside the Nitro process (see
`v4.2-service-inventory.md` §4). For the control plane this means:

1. **The web process is not restartable.** Restarting Nuxt to apply a config
   change kills the bot supervisor and both AI loops. `BOT_EMBEDDED` /
   `AI_AGENT_EMBEDDED` / `AI_REVIEW_EMBEDDED` exist, but the default is embedded.
2. **`/operations` cannot stop what it shows.** There is no handle to the
   embedded loop from an API route — it is a module-level closure inside a Nitro
   plugin.
3. **Two supervisors can coexist.** `services/run.mjs watch` (manual) and the
   embedded plugins are independent. Nothing prevents running both, and the bot
   lease is the only thing that stops double-processing.
4. **Dev reload duplicates loops.** Each `nuxt dev` reload re-runs the plugin; the
   bot nonce is stable (`embedded-${pid}`) so leases are adopted, but the AI
   plugins have no such guard beyond module-level memoization.

## 7. Security and authority findings

| # | Finding | Severity | Status | Evidence |
| --- | --- | --- | --- | --- |
| S1 | `run-once` and `reprobe` check identity but **not capability**. Any authenticated Hub user can spawn a detached Node process on the host. | **high** | **Fixed** | both handlers now call `requireRootEvent(event)` after `requireOwnerId(event)`; asserted by `tests/service-control-authz.test.ts` |
| S2 | `spawn(..., env: { ...process.env })` passes the entire server environment (Mongo URI, AI keys, `AUTH_JWT_SECRET`, Telegram token) to the child | medium | **Fixed** | the detached spawn is gone: the endpoint enqueues operations, so no child inherits the server environment |
| S3 | No audit record for a process-spawning action | medium | **Fixed** | every enqueued operation is recorded and audited by the supervisor |
| S4 | No idempotency: repeated POSTs stack processes | medium | **Fixed** | one batch key suffixed per service; the supervisor also refuses a second active operation per service |
| S5 | `reprobe` comment claimed to write heartbeats but does not | low | **Fixed (wording)** | handler doc-comment now states it re-reads status |
| S6 | Response leaks `ownerId` and the full service list to any caller | low | **Fixed** | the response is `{ batchKey, requestedAt, count, accepted: [{ serviceId, operationId }] }` |

All six findings are now closed. S1 was the priority — a remote process-spawn
primitive behind a single valid session — and is fixed with a root-only guard
(`requireRootEvent`) that proves *privilege*, not only *identity*. S2–S6 were not
patchable inside the legacy handler, so they were retired the honest way: the
endpoint still exists (the dashboard button keeps working) but it no longer spawns
anything. It enqueues a real `run-once` operation per service for the supervisor
and answers `202 Accepted` with the operation ids, so a control action now carries
an audit row and an idempotency key instead of a detached process.

## 7.1 Live rollout findings (S3 Step 2)

The supervisor was run against the real registry (`node services/supervisor.mjs run`,
isolated state file) and all 13 non-destructive supervised periodic services were
started through the command inbox. Four defects surfaced that the unit tests could
not see, plus one observed-but-correct behaviour (R5 came from the follow-up work of
driving that supervisor from inside Nitro, which is what the dashboard does).

| # | Finding | Severity | Status | Evidence |
| --- | --- | --- | --- | --- |
| R1 | **Leases were never renewed.** A lease was claimed only at spawn, with a 30 s TTL, and nothing refreshed it — so ~30 s after every start the lease expired and the overlap guard saw nothing to skip, which is exactly the duplicate-producer hazard §17.15-O4 exists to prevent. Live, with 13 services supervised, `node services/run.mjs plan` reported **0 blocked / 14 runnable**. | **high** | **Fixed** | `renewHostedLeases()` now renews (or takes over an expired) lease for every instance the process hosts, each tick. Regression test `the lease is renewed while the instance is alive, so the guard keeps blocking`; the live re-check reports **13 blocked / 1 runnable** with one `[guard] SKIP <service>: supervisor lease held by <id>` per service. |
| R2 | **A recovering dependency was treated as a hard block.** `evaluateDependencies` read `observed: FAILED` as terminal, so when a batch of starts is consumed in a single tick — a supervisor restart, or 13 cold starts — a service whose dependency had crashed was failed instantly instead of waiting for that dependency's own restart. Live: `alertRules`, `brief`, `confluence` and `regime` failed with `DEPENDENCY_NOT_READY: scanner:FAILED, funding:FAILED` while both dependencies were coming back in the same tick. | **high** | **Fixed** | a dependency with `desired: RUNNING` is now *waited for* (the operation parks as `awaiting-dependency`, and the operation TTL bounds the wait); `DEGRADED` stays a hard block under `REQUIRE_READY`. Covered by two regression tests in `tests/supervisor.test.ts`. |
| R3 | **A dependency the supervisor cannot start gated forever.** `signals` depends on `market-plane`, which is hosted inside the Nitro process (`supervised: false`), so its record can never be observed READY and every start failed with `DEPENDENCY_NOT_READY: market-plane:UNKNOWN` — the signal producer could not be started at all. | **high** | **Fixed** | `evaluateDependencies` skips dependencies whose definition is `supervised: false`: the supervisor must not gate on a lifecycle it does not own, and those services report their own `dependency-reachable` evidence. Regression test `ignores a dependency that another process hosts`. |
| R4 | `news` and `liquidation` settle at **DEGRADED** because the optional `output-produced` rule fails ("the last cycle produced no output") while every required rule passes. | — | **Correct by design** | §17.4 separates required rules (the READY gate) from optional ones (downgrade to DEGRADED, never FAILED). A 10-minute news poll with no new items is a healthy empty cycle, not a fault. |
| R5 | **A worker died whenever its control plane restarted.** `process.send()` on a closed IPC channel does not throw: Node emits `error` on `process` (or calls the callback when one is supplied). `services/workerHost.mjs` did neither, so the next heartbeat became `uncaughtException: ERR_IPC_CHANNEL_CLOSED` inside the `fatal()` handler and every worker exited 1 with a stack trace on every supervisor / Nitro restart or HMR pass. | **high** | **Fixed** | `send()` now passes a callback (`process.send(message, undefined, undefined, cb)`) and a `process.on('error')` listener catches the `ERR_IPC*` case; both funnel into `noteChannelLoss()`, which logs once, keeps the pid alive for `WORKER_CHANNEL_GRACE_MS` (default 5 min) so the next supervisor can ADOPT it by pid, then exits 0 if nobody claims it — an unsupervised producer must not keep writing. Regression test `tests/worker-channel.test.ts` forks the real worker host and closes the channel. |

Result after the fixes (one live daemon, real providers):

| Service | observed |
| --- | --- |
| `funding`, `scanner`, `regime`, `confluence`, `crossScan`, `macro`, `newsExtract`, `reconcile`, `alertRules`, `signals`, `brief` | READY / HEALTHY |
| `news`, `liquidation` | DEGRADED (optional `output-produced` rule only) |
| `retention` | deliberately not started — it purges data by policy, which is an operator decision |

`/operations` then reads the same state: `GET /api/v1/operations/services` returned
`ready: 10, degraded: 3, active: 13, failed: 0, planned: 3, unknown: 8`, and
`node services/run.mjs plan` prints one `[guard] SKIP` per supervised service — the
legacy orchestrator can no longer run a second copy of anything a supervisor owns.

Operational note: the CLI daemon that produced this evidence was stopped again, so it
was not left enabled. The dashboard now has an embedded driver
(`server/plugins/service-supervisor.ts`) with its own escape hatches
(`SERVICE_SUPERVISOR_EMBEDDED=off`, `SERVICE_SUPERVISOR_AUTOSTART=off`); it deliberately
never drains workers on shutdown, so a Nitro restart is a *control-plane restart*, not a
drain — see `v4.2-service-inventory.md` §14 and `runbooks.md` §11.

## 9. What S1 and S2 must build

### S1.1 — registry (no behaviour change yet)

A machine-readable service registry, one entry per service:

```
{ id, label, group, entry, intervalSec, scope: 'system'|'owner'|'account'|'session',
  dependencies: string[], killSwitch?: string, supports: ['start','stop','restart','reset','probe','run-once'],
  readiness: { requires: string[] } }
```

The 18 rows are already enumerated in `v4.2-service-inventory.md` §3–§4, so the
registry is a transcription, not a design exercise. Keep `services/run.mjs` as the
executor until S2; the registry only *describes* it.

### S1.2 — state machine

```
observed: UNKNOWN -> STARTING -> READY -> DEGRADED -> STOPPING -> STOPPED | FAILED
desired:  RUNNING | STOPPED
```

`READY` requires: process alive **and** dependencies reachable **and**
subscription/init complete. `DEGRADED` requires `READY` first, then a failed
freshness/functional check. This split is mandatory: merging them means a feed
that just subscribed is never READY, and a dead feed stays READY.

### S1.3 — probe that probes

Replace the file re-read with a real check per service: Mongo ping, provider
handshake, last-output age. Return `{ dependency, capability, latencyMs,
lastSuccessAt, freshness }` per dependency. Do not mutate desired state.

### S2 — supervisor + durable commands

- **services/supervisor.mjs** (planned) as a separate process, started by the OS
  wrapper (nssm/Task Scheduler on win32, systemd on Linux), never by Nitro.
- Mongo collections: `service_definitions`, `service_state`, `service_operations`,
  `service_events`.
- Command flow: `POST .../start` → validate capability + scope + dependencies →
  persist operation (`QUEUED`) → `202 { operationId }` → supervisor claims →
  `STARTING` → readiness proof → `SUCCEEDED` + `observed: READY`.
- Conflicting concurrent operations rejected by `(serviceId, scopeKey)` lock.
- Graceful shutdown via IPC message + drain timeout (win32 `SIGTERM` is a hard
  kill, so a signal-only drain will not work).
- `run-once` becomes a durable job record with its own `operationId`, not a
  spawn-and-hope.

### S2 — Operations UI

Rebuild `operations.vue` as the §17.9 table: Service / Scope / Desired / Observed /
Health / Last heartbeat / Last successful work / Data freshness / Workload /
Actions. Detail drawer with Overview / Activity / Logs / Jobs / Data /
Configuration / Audit. Keep the existing KPI strip and console tabs as a second
section, not the whole page.

UI rules from §17.8: disable conflicting controls, show phase text, never set the
badge from the click response, `UNCONFIRMED` on timeout, restore in-flight
operations after refresh.

## 10. Acceptance tests to add (S2)

These are the §17.14 tests, expressed against this repo:

1. `start` on a stopped service returns `202` + `operationId`; polling reaches
   `SUCCEEDED` **and** `observed: READY`; the readiness checklist is non-empty.
2. `start` twice concurrently: the second returns a conflict, not a second
   process.
3. `stop` reaches `STOPPED` and the lease is released; a `start` immediately after
   succeeds.
4. Kill the worker process externally: within one heartbeat interval the state is
   `FAILED`, not `READY`.
5. Point the service at an unreachable Mongo: state is `FAILED` (dependency), and
   the UI shows a dependency error, not a generic failure.
6. `probe` on a healthy service returns latency + freshness and does **not**
   change desired/observed state.
7. `run-once` creates a job record and the UI can show its completion; the
   response is `202`, not `200 success: true`.
8. A user without the `services.*` capability gets `403` on every mutation
   (regression test for S1).
9. Operations renders the exact §17.9 columns from the API, not from the
   heartbeat file directly.
10. Restarting the web process does not stop a supervised worker.
